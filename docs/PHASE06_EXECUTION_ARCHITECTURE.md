# Phase 06 — Trading Execution Engine Foundation Architecture

This document details the architectural foundation and execution pipeline design for the Trading Execution Engine implemented in Phase 06 — Stage 01.

---

## 1. Architectural Overview

The Execution Engine resides strictly within the Application and Domain boundaries, depending entirely on abstractions and remaining exchange-agnostic.

By avoiding direct dependencies on Bybit-specific or third-party client SDKs, the engine supports multiple exchange integrations (e.g., Bybit, Binance, OKX) seamlessly without core workflow modifications.

### Target Execution Pipeline

```text
       Phase 05
Approved Trade Decision (RiskDecisionStatus == Approved)
          ↓
  TradeExecutionRequest
          ↓
   ITradeExecutionService (TradingExecutionService)
          ↓
     IOrderValidator (OrderValidator)
          ↓
      IOrderBuilder (OrderBuilder)
          ↓
   IExchangeTradingGateway (TestExchangeTradingGateway / Bybit Adapter in Stage 03)
          ↓
   ExecutionResult (Success / Failure / Rejected status mappings)
```

---

## 2. Domain Models

All execution domain models reside in `TradingBot.Application/Trading/Execution/Models/` to decouple execution logistics from underlying infrastructure details.

### 2.1 TradeExecutionRequest
Represents the incoming payload from Phase 05 representing an approved risk profile ready for immediate execution.
- `Id`: Unique request identifier.
- `SignalId`: Reference to the original parsed Signal.
- `RiskEvaluationId`: Reference to the calculated risk profile.
- `Symbol`: Target trading pair (e.g., `BTCUSDT`).
- `Side`: Side of the trade (`OrderSide.Buy` or `OrderSide.Sell`).
- `OrderType`: Order type (`OrderType.Market` or `OrderType.Limit`).
- `Quantity`: Decimal target quantity.
- `Price`: Decimal limit price (required for Limit orders).
- `Leverage`: Selected leverage.
- `RiskDecision`: Phase 05 authorization verdict (`RiskDecisionStatus`).
- `CreatedAt`: Creation timestamp.

### 2.2 OrderRequest
Mapped exchange-agnostic request format generated by `IOrderBuilder`.
- `Symbol`: Normalized symbol name.
- `Side`: `OrderSide`.
- `Type`: `OrderType`.
- `Quantity`: Decimal size.
- `Price`: Decimal entry price.
- `SignalId` / `RiskEvaluationId`: References.
- `ClientOrderId`: Unique client-generated correlation ID (e.g., `BOT-{guid}`).

### 2.3 ExecutionResult
The normalized status returned to the caller indicating success or specific structural/rejection causes.
- `Success`: Boolean outcome flag.
- `OrderId`: Generated Order identifier.
- `ExchangeOrderId`: The target exchange platform's order receipt ID.
- `Status`: `OrderStatus` enum values (e.g., `Filled`, `Rejected`, `Failed`).
- `Message`: Informational or error description.
- `ErrorCode`: Domain-specific error code.

## 3. Core Service Contracts & Implementations

### 3.1 ITradeExecutionService / TradingExecutionService
Co-ordinates the entire execution sequence:
1. Validates structural and boundary constraints of the execution request via `IOrderValidator`.
2. Automatically rejects unapproved or invalid state sequences (returning a descriptive `ExecutionResult` with `OrderStatus.Rejected`).
3. Constructs an exchange-agnostic order specification via `IOrderBuilder`.
4. Dispatches the order to the registered `IExchangeTradingGateway`.
5. Propagates mapping or platform errors back gracefully without leaking native API details.

### 3.2 IOrderValidator / OrderValidator
Enforces domain rules before any external exchange gateway call:
- **Rule 1 (Boundary Check):** Risk decision must equal `RiskDecisionStatus.Approved`. `Rejected`, `NeedsManualReview`, and other states are immediately blocked.
- **Rule 2 (Quantity Check):** Quantity must be strictly greater than zero.
- **Rule 3 (Type/Side):** Assures valid defined system states.
- **Rule 4 (Limit Price):** For Limit orders, Price must be strictly greater than zero.

### 3.3 IOrderBuilder / OrderBuilder
Constructs the standard `OrderRequest` from the validated execution request, generating a unique `ClientOrderId` using the `BOT-` prefix.

### 3.4 IExchangeTradingGateway / TestExchangeTradingGateway
Abstraction representing the gateway to the exchange APIs. During Stage 01, a highly-configurable `TestExchangeTradingGateway` mock is utilized for tests, ensuring 100% test isolation without network dependencies.

## 4. Error Handling and Resiliency

The Execution Engine defines clean, targeted execution exceptions:
- `ExecutionValidationException`: Thrown when structural or state constraints fail.
- `OrderConstructionException`: Thrown on internal builder mapping failures.
- `ExchangeGatewayException`: Wraps any low-level transient or exchange-specific platform exceptions.

All service signatures natively propagate a `CancellationToken` to ensure responsive task cancellations without thread blockages.

---

## 5. Structured Logging & Auditing

Comprehensive, redacted execution logging is fully integrated into `TradingExecutionService` using the following standardized structured event logs:
- `ExecutionRequested`
- `ExecutionValidationStarted`
- `ExecutionValidationPassed`
- `ExecutionValidationFailed`
- `OrderBuildStarted`
- `OrderBuildCompleted`
- `ExecutionCompleted`
- `ExecutionCancelled`
- `ExecutionFailed`

All logs strictly redact API Keys, Secrets, and Credentials, preserving the system's strict security posture.
